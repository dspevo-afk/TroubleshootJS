# Solver finite-validation ownership audit

Read-only review of `86aa58bc6d7f8909d1519a57da6ab1d094a23c48` plus the current dirty `CirSim.java`. No build, test, or source edits were made. References below are current source line numbers.

## Validation flow

- **Analyze/stamp:** `analyzeCircuitOwned` calls `stampCircuit` (2737, 2802–04). Linear `stamp()` writes matrix entries through `stampMatrix` (3188–3208), which checks the incoming stamp and accumulated matrix cell; mapped constant-column writes check the adjusted RHS (3194–98). Direct `stampRightSide(int,double)` additions are not checked (3224–32). `simplifyMatrix` constructs a new reduced matrix/RHS (2943–60), then copies them into `origMatrix`/`origRightSide` (2961–65). The post-simplification `requireFiniteMatrix` at 2843 checks the reduced matrix, but not the RHS or constant-row values. It is needed for nonlinear analyses, which do not factor during analysis. Linear analysis factors immediately (2850–54) and rescans the result at 2855.
- **Each nonlinear trial:** after `beginTrial`, restore RHS from `origRightSide` and matrix values from `origMatrix` (3347–63), then run element `doStep()` before factoring (3362–91). Source-wide write search found the trial's matrix writes only in `stampMatrix` (plus the restore and factor writes); all current `doStep` matrix updates use that checked adapter. Each nonlinear factor invocation scans every input matrix entry for finiteness and zero rows (CirSim 8025–42), then checks reciprocal, multipliers, and every elimination update (8075–8103). The input scan is repeated on every factor attempt.
- **Solve and apply:** `lu_solve` itself has no finite check (8117 onward). Immediately afterward the executor scans the reduced `circuitRightSide` (3395–97). `applySolvedRightSide` scans every original row before mutating currents or node voltages (3485–94); nonconstant rows read values already checked in the reduced RHS, but constant rows use `RowInfo.value` and need this guard. It then copies full-row results to node voltages / voltage-source currents and calls `setNodeVoltages` (3495–3519); `nodeVoltages` is checked at 3399.
- **Accepted-state publication:** before publication, accepted-step code advances time, calls model `stepFinished`, wire-current and scope callbacks, and copies `nodeVoltages` to `lastNodeVoltages` (3431–51). `CircuitSolverExecutor.accepted` then rechecks `nodeVoltages` and RHS before dispatching events, accepting the boundary time, and staging observation samples (195–200). The boundary independently requires finite, advancing time (SolverExecutionBoundary 109–13). The observation service rejects a nonfinite differential sample, including overflow of the voltage subtraction (SolverTimeObservationService 132–46), and only commits staging after a complete operation (149–76).

On numerical exceptions, `lu_factor` clears workspace references/counts in `finally` (CirSim 8109–11). The owned executor classifies the failure and calls `finishOperation`; unsuccessful/cancelled operations discard staged observations and do not publish a solver observation (CircuitSolverExecutor 107–10, 229–35; SolverTimeObservationService 149–76). Factor failure can leave a partially factored matrix, but subsequent nonlinear trials restore `origMatrix`; the operation that failed does not accept/publish. A singular factor returns `false`, and callers stop the circuit (CirSim 2850–53, 3387–91).

## Redundancy findings / decision

**Largest plausible hot-path opportunity, conditional GO:** the per-entry finite predicate inside the repeated nonlinear `lu_factor` input preflight (8025–42) has a checked-producer proof on the current owned path. The baseline values copied from `origMatrix` were copied from the post-simplification matrix and are covered by 2843; every dynamic matrix write in `doStep` goes through `stampMatrix`, which checks both input and result. `origMatrix` is a separate value copy, and trial restore occurs before `doStep`; factor row swaps/updates happen only after the preflight. The remaining row scan still serves zero-row/singularity detection, so this finding does **not** justify skipping that scan or changing factor arithmetic/checks. A dedicated trusted owned-factor entry could omit only the repeated input `requireFiniteStamp` predicates while retaining the zero-row scan and all arithmetic checks. Keep both existing general APIs fully validating. **GO only if** an isolated measurement attributes meaningful cost to those predicates and the fast path is restricted to this current restore + checked-stamp call sequence; otherwise NO-GO. This audit does not itself authorize implementation.

Two smaller exact duplicate checks exist:

1. The post-factor matrix scan at 2855 is redundant after a successful linear factor: input cells were checked, and every changed result was checked by the factor; no write occurs before the scan. The pre-factor scan at 2843 is still needed for nonlinear analysis and for simplifying output.
2. The mapped/nonconstant entries in 3488–94 are already covered by the immediately preceding reduced-RHS scan at 3397; only `ROW_CONST` values add coverage there. Likewise, node values copied from those validated full rows are rescanned at 3399. `accepted()` then rescans both arrays at 197. A write-site search found no current writes to these arrays between those checks (RHS writes are at 3231, 3355, and the solve; node writes at 3504; `Task41SimulationSnapshot` restores occur at separate proof/cleanup boundaries). These are current-source redundancies, but the accepted-boundary checks are intentionally located after step callbacks and immediately before publication; retain them unless the owner explicitly accepts that boundary tradeoff. None is a reason to weaken the full-row constant check, solver-time check, or observation sample finite guard.

## Caller and semantic limits

The three-argument `lu_factor(a,n,ipvt)` always delegates to the fully validating workspace overload (8021–27). `invertMatrix` uses that API (8841–44); its only production caller, `CustomTransformerElm.stamp` at 319, factors a locally built inductance/coupling matrix, not the analyzed solver matrix. `LuFactorizationChecks` also exercises both overloads with NaN and ±Infinity (70–90). Those callers have no stamp-provenance guarantee; preserve the full input scan there.

The proposed owned-path proof depends on current ownership/write-site facts, not numeric value equivalence: preserve pivot ordering, row-zero `!= 0`, zero-pivot handling, and all checked arithmetic. `SolverExecutionBoundary.finite` accepts signed zero and finite subnormals; `== 0` behavior remains unchanged. Any new direct matrix writer, restoration during an active operation, or call using an unvalidated matrix invalidates the proof and must use the general checked factor path. Existing caught `Failure` behavior must remain numerical failure with operation sample cleanup; do not turn it into a different exception or partial accepted result.
