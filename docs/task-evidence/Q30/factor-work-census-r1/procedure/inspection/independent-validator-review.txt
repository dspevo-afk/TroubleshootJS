Count conservation is aligned with the census contract. It uses all `luFactorTimingAttempts` as the denominator, checks `selected == timerSelected // 8`, and conserves completed plus failed calls both globally and by matrix size. It ties selected dimensions to current sampled-size counts, sums matrix-input samples/attempts to the selection total, and sums outcomes back to top-level totals. The requested target arithmetic is 1,453 timer-selected calls → 181 census calls, and 90 → 11; it does not confuse this with the 742,391 full factor-call count. Partial failures are bounded rather than claimed exact. The companion note explicitly discloses the known malformed-short-row case where `upperColumnProbes` pre-adds the valid square-loop bound before an access can throw.

One negative-canary fragility: `negative_canaries()` applies “successful factor triangular undercount” to `next(iter(byMatrixSize.values()))` and sets that dimension’s `pivotSearchCandidates` to zero. If the first dimension has only early failed/preflight-rejected factors and no successful body, zero is admissible under the validator’s partial-failure bounds, so this corruption is not guaranteed to reject. Choose a dimension with `factorCompletions > 0` or omit that specific mutation when no such dimension exists. This is a canary-generation issue, not a count-acceptance weakness.

Evidence boundary: the target 181/11 figures are derived expectations here, not observed census results. The predeclared off/profile plan exists, but its `factor-work-census-01-off-10014.log` is empty; focused native/GWT gates do not validate actual cold/warm Q30 census distributions or run `negative_canaries()` on those reports.
