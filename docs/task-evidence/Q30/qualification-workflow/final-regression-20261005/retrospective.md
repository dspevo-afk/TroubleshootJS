Q30 was difficult for two different reasons: the electrical problem is demanding, and the qualification process accumulated too many moving parts. This retrospective proposes future work only. It does not authorize a budget, oracle, architecture or public-catalog change in the current continuation.

- **Product and solver complexity:** Purposeful 20–40-part circuits must route physically, preserve endpoint identities, show a meaningful fault, support five diagnostic hypotheses and verify restored customer behavior using the live CircuitJS graph. Power transitions and stored energy make apparently simple UI actions depend on actual solver advancement. This complexity is real and should stay visible in the contracts.
- **Genuine performance and correctness problems:** Earlier normal requests exceeded the fixed 90-second limit. Solver/routing improvements and family-owned generation work were necessary; private 300-second passes did not establish normal acceptance. The latest charged-relay problem was a developer-canary timing defect: ordinary isolated settlement advanced the solver and discharged the coil before charge capture. The fix preserves actual electrical guards and solver cadence. The previously observed 90.621-second cold timeout has no proved code-cause attribution; the fresh cohort passes under the same limit.
- **Harness and adapter defects:** Real failures included PowerShell reserved-variable collisions, an unsupported publication parameter, native versus CIM birth precision, obsolete snapshot fields, and copied helpers with stale source/head pins. The release checker also classified a live row with unavailable identity metadata as absent; that now has a tested fail-closed correction. These failures are separate from product physics and must not be reported as electrical failures or successful qualification.
- **Coordination:** Timing qualification shared Windows with other projects and needed a real quiet allocation. Browser-input capability was unavailable for fresh visible QA. A stable test host and an early capability check would make these limits predictable. There is no measured percentage of time attributable to contention or approvals.
- **Overhead we introduced:** Layered pointers, role bindings, snapshots, per-helper hashes, repeated copies and custom launch/release wrappers have become disproportionate. After the electrical cohort and controller passed, the strict zero-unrelated-PID-reuse predicate still blocked release. We are now reviewing tens of kilobytes of new detached-observer code to avoid observation-created process churn. That is qualification cost, not simulator progress. The current predicate remains unchanged until separately approved scope changes it.

The current candidate's measured gates show why fast feedback matters: native83 took 3,918.455 seconds (about 65 minutes), compiled31 2,944.978 seconds (about 49 minutes), and the cold77 controller 4,440.490 seconds (about 74 minutes). Isolated and shipping five-permutation builds took 82.844 and 81.496 seconds. These are separate measured operations, not a decomposition of total project time. Cold77 is 77/77 PASS with a worst application case of 85.003 seconds; independent release and overall acceptance remain separate and incomplete at this retrospective's cutoff.

Ranked practical changes:

1. **One maintained qualification runner and receipt schema — high impact, moderate effort, separate implementation scope.** Make current native, compiled, normal-admission and menu gates consume one candidate manifest and emit directly named results. Keep independent electrical expectations. Retire copied adapters and obsolete formats instead of carrying compatibility layers for development versions. First consolidate the existing contracts; do not replace the solver or rewrite all tests.
2. **Exact process-instance ownership — high impact, small focused scope.** Keep retained process handles or PID plus authoritative precise birth and image. A proven different birth establishes that the recorded instance is gone; unknown birth/image remains unresolved. Consolidate Windows Job Object ownership and ordinary host cleanup through the maintained implementation. Replace the zero-unrelated-PID-reuse acceptance condition only through explicit scope and real positive/negative Windows canaries. Never kill by bare PID, process name or broad browser enumeration.
3. **A small usable feature slice before the final matrix — high impact, low workflow effort.** At the next authorized milestone, define one representative deterministic board and one meaningful negative case up front. Prove healthy behavior, fault symptom, real diagnosis, a valid repair and customer retest through supported visible input early. During implementation run the affected contract checks and canaries. Freeze source once, run the required complete final matrix once, and rerun only gates whose consumed inputs or relevant behavior changed. Task-required fresh checks still take precedence.
4. **Predictable host and input capability — medium impact, low coordination effort.** Reserve one serial timing window on an idle host. Confirm JDK8/GWT, the real process implementation and visible-input tooling before a long matrix. Treat missing prerequisites as explicit blockers early. A dedicated qualification host is an optional infrastructure improvement, not a requirement to add more servers or change this PC now.
5. **One source binding and one run manifest — high impact, moderate architecture effort.** Automate candidate/source identity, pinned tools, outputs and resource ownership once. Let gate results refer to that manifest rather than manually propagating hashes through multiple role files. Preserve raw failures and a portable evidence summary, but stop maintaining redundant parallel ledgers and bespoke wrappers. Do this after Q30 acceptance under separate scope.

Stop rebuilding unchanged production inputs for documentation or helper-only edits; copying helpers for each continuation; accepting stale receipts because they look green; creating wrappers around wrappers; and treating headless/controller calls as visible-player proof. Do not spend another feature milestone expanding qualification scaffolding without a concrete failing boundary it must prove.

Keep CircuitJS as electrical truth, independent oracles, bounded generation and mutation, stable physical/electrical identities, exact signed-long determinism, normal-player privacy, real temporary-resource cleanup and the unchanged 90-second/640-unit/5-second contracts strict. Keep representative regression seeds and preserve failures. The simplification target is orchestration and feedback speed, not weaker product correctness.

For the next feature, agree on a small acceptance card first: intended player behavior, owned code boundary, representative seed, negative/wrong-repair case, visible-input proof, focused gate and final gate. Implement the complete vertical slice, show its usable behavior, then broaden only where the feature requires it. U06/U07/Q60 remain unstarted; the parent owns Q30 acceptance and the next roadmap phase.
