# Passive pose policy: post-verdict cause-observer plan

## Scope and current evidence

This is a read-only source review and a bounded plan for a later observational trace. It does not change the rejected policy result, gate criteria, search, or routing behavior.

The strict 14-row result remains **FAIL**: 12 rows are exact to placement interpretation 15 (density 14) and seeds 42 and 3 are not. Both changed rows selected candidate 1. In the archived `selected-effects.json`, seed 42 changes from area 5,519,502 to 6,034,252 (+514,750), largest protected empty rectangle 178,200 to 208,000 (+29,800), copper Manhattan length 42,230 to 49,860 (+7,630), and 45 to 48 vias. Seed 3 changes from area 5,557,320 to 5,561,172 (+3,852), protected empty rectangle 277,200 to 230,400 (-46,800), copper 41,650 to 45,370 (+3,720), and 47 to 48 vias. The recorded route-profile outcomes and selected attempt are the same across the two interpretations; that does not imply the candidate's internal placements or router input were the same.

Candidate 1's recorded demand rises by 3,000 for each row. Its recorded raw outline rises from 5,860,800 to 5,894,100 for seed 42 and stays 5,508,000 for seed 3. These are direct observations, not a finding that sizing alone caused either final routed delta.

## Existing source seams and order

The exact policy source archive is under `source/`; the planner below is the archived policy-run source, not a reconstruction from current output.

1. `PcbPlacementConstraints.passivePosePolicyVersion` is validated as a supported interpretation; policy 1 also has the density-14, medium-board, two-layer compatibility condition. The two run inputs differ by this explicit interpretation while retaining density 14.
2. In `PcbPlacementPlanner.plan`, the requested candidate is remapped to `algorithmCandidate` before the `Random` seed is formed. For the repeated-control density-14 candidate-1 branch, both versions map to algorithm candidate 0. The seed expression is therefore the same. Policy sizing is separately gated by policy 1, density at least 10, requested `candidate == 1`, medium-board size, and repeated control regions. Each declaration still calls the same registry creation once, in the same declaration order.
3. `Item` retains the selected TOP0 `footprint` and original `envelope`; on the enabled non-anchor branch it additionally holds `passivePoseAlternative`, `alternateEnvelope`, and conservative `sizingEnvelopeWidth`, `sizingEnvelopeHeight`, and `sizingDemandArea`. The alternative is derived from the already-created physical geometry. `plan` accumulates the conservative demand and width/height only for the enabled eligible branch; anchors retain their provider-pose sizing. This is the first policy-dependent sizing input, before any placement visit.
4. `planMedium` derives `targetArea`, `aspect`, `contentWidth`, `maxWidth`, `maxHeight`, outline, and possibly `boundaryX`. For a single-barrier repeated-control board, `boundaryX` also uses each item's `sizingDemandArea`; an unchanged final outline therefore does not rule out every sizing-mediated target change.
5. Placement order is deterministic but data dependent. Anchors sort by hint `yFraction` then component ID. Non-anchors start in a component-ID `TreeMap`; `chooseMediumItem` recalculates its connectivity score against the already placed prefix, with a seed/candidate hash as a small tie breaker. When the barrier override applies, it scans the remaining values in component-ID order and selects the first qualifying isolation-body item. Record the actual chosen item and prefix rather than infer order from component IDs alone.
6. In `mediumPlace`, the search target and advisories are calculated from the retained source `item.footprint` (TOP0 for the four canonical passives): `preferredX/Y` use its placement width/height; `weightedConnectedTarget` uses its pads; `PcbSupportPairPlacement.find` receives it; and the region/group, boundary-package and vacancy guidance are formed before visit selection. In density 14, the vacancy path can use `vacancyDomainBox`, `PcbVacancyTargets.targets` and `nearest`; its `sourceEnvelope`, source origin, preference and vacancy pocket use TOP0. These are concrete TOP0 centering/support/vacancy inputs while the later trial can be TOP90.
7. For a non-anchor ring item, existing ring ordinals are `ring * count + index`, with six visits per ring for rings 0 through 20 (126 visits maximum for that item). `MEDIUM_STEP` is 40. The literal requested offsets in slot order are `(direction*step,0)`, `(-direction*step,0)`, `(0,+step)`, `(0,-step)`, `(direction*step,+step)`, `(-direction*step,-step)`. At ring zero, all six offsets are `(0,0)` before vacancy substitution; slots 1–5 are replaced by the first up to five vacancy points. `PcbVacancyTargets.targets` removes duplicate points within that list, but a vacancy point may still coincide with the base origin. At rings above zero, there is no vacancy substitution. For the four canonical passives, policy 0 supplies TOP0 at every slot and policy 1's `forVisit` supplies TOP0 on even ordinals and TOP90 on odd ordinals. Other items keep their provider pose, including UFB TOP180. Thus existing TOP0 visits at odd slots are replaced by TOP90 visits; the loop does not add visits.

   For `direction == 0`, ring slot 0 requests `(baseX,baseY)` at all 21 rings. Its ordinal `ring*6` is always even, so policy 1 keeps TOP0 for every one of these repeated requests. Within each ring above zero, slots 2 and 4 both request `(baseX,baseY+step)` and are both even/TOP0; slots 3 and 5 both request `(baseX,baseY-step)` and are both odd/TOP90. Thus the down-origin's two policy-0 TOP0 visits are both replaced by TOP90, while the duplicate up-origin retains two TOP0 visits. Within a single `mediumPlace` call those same-template duplicate requests have identical post-`mediumGridOrigin` coordinates, since the placed prefix, outline and source template do not change during the visit loop. Slots 0 and 1 also request the same center at each ring, but use different templates under policy 1, so equal post-clipping coordinates are not guaranteed. At ring zero, the duplicate pairs can be broken by vacancy substitution; only slot 0's base request is unconditional. For `direction == +1` or `-1`, all six offsets at every ring above zero are distinct and no requested offset repeats across different positive rings; different requests can still collapse at outline clipping, but source alone does not guarantee that. These are visit-sequence facts only: no new schedule or acceptance claim follows from them.
8. Each visit is clipped once by `mediumGridOrigin` using that visit's active footprint envelope, translated once, passed to the existing `fits` once, and, if it fits, scored once. The score and final fit use the actual visit template. The strict `score < bestScore` update retains the earliest equal-scoring visit. If no ring candidate fits, fallback grid bounds are initially computed from TOP0, then each existing sequential fallback visit selects its pose and clips that trial with its active envelope; the loop keeps its existing first-fit break. The global evaluation counter and limits remain in these same branches.
9. After all items are selected, `PcbPlacementCompactor.compact` can translate footprints and shrink the outline along its two axes. Capture the `Plan` before and after this existing call; otherwise compaction could be mistaken for a ring-search divergence. Then use the already-existing candidate-selection and route result records. The observer adds no candidate or route invocation.

## Bounded observer plan

For the already authorized fixed rows (42 and 3), compare placement interpretation 15 (density 14) with explicit interpretation 16 (density 14) at the same candidate-1 call. Use the normal four-route reproduction only as already scheduled by the root; do not add route calls for tracing. Capture a bounded in-memory record and flush it after planning, so no per-visit file I/O affects the loop. Keep the observer read-only: no extra registry creation, random calls, pose construction, `mediumGridOrigin`, `fits`, score evaluation, candidate search, evaluation-counter increment, or router call. Do not read private `Random` state; matching source-creation order and geometry is the safe observable boundary.

The record should include:

- Header: seed, requested candidate, `algorithmCandidate`, density/policy versions, part count, and route-profile identity.
- Sizing: declaration ordinal and component ID; resolved anchor; region/domain; TOP0 geometry identity and rotation; original and alternate envelope rectangles; per-item sizing area and extents; aggregate `demandArea`, `courtyardArea`, `maxWidth`, `maxHeight`, `anchorWidth`; then `targetArea`, aspect, content width, outline and `boundaryX` inputs/result.
- Per-item prefix: place ordinal and component ID; all earlier selected `(componentId, origin, rotation, geometry identity)` tuples; anchor/remaining path; hint fractions; connected target; preferred target before and after group/boundary adjustment; direction; support pair identity/target; vacancy origins, selected preference and pocket. This makes an order change distinguishable from a pose choice at a fixed prefix.
- Per existing visit: ring/index or fallback ordinal; requested origin before clipping (after any existing ring-zero vacancy substitution); active template rotation/geometry; active envelope; actual clipped origin; the existing fit result; existing score and any terms captured during that same calculation; and whether it replaced the incumbent. Record fallback bounds/start/total only when the existing fallback branch runs. Do not calculate scores or fits for the unselected counterfactual pose.
- End of item and plan: selected footprint pose/origin, score, fallback flag, evaluation-count delta; then pre- and post-compactor outline and ordered footprint geometry/origins. Keep compactor evaluation accounting separate from search visits.

## Independent expectations and interpretation

The trace should satisfy these source-level expectations before anyone interprets a delta:

- Policy 0 keeps the four canonical passive templates at TOP0. Other items retain their provider pose, including UFB at TOP180. Policy 1 may select an alternate only on the existing candidate-1 repeated-control medium non-anchor branch and the canonical `AXIAL_RESISTOR`, `AXIAL_DIODE`, `RADIAL_ELECTROLYTIC_CAPACITOR`, and `RADIAL_CERAMIC_CAPACITOR` packages; all other candidates/items retain their provider pose.
- Each ordinary ring/fallback visit has exactly one active template, one existing clipping, at most one existing fit, and at most one existing score. There are no new origins or router calls. For a non-anchor item the full ring ceiling remains 126 visits; actual totals may be lower only through the existing global cap/rejection.
- Until a first divergence, declaration/registry sequence, item order, complete prior placed prefix, outline, and guidance inputs must match for a visit to support a direct pose-effect comparison. Match traces by candidate, component, and ring/index or fallback ordinal, not just final component order.
- On a matched odd ordinal with the same prefix, outline, requested origin, and clipped origin, interpretation 15's TOP0 trial is the existing baseline for the location where interpretation 16 tests TOP90. A change in fit/score at that point is evidence of the actual pose substitution at that existing visit. If outline, prefix, target, or clipping differs first, record that earlier cause and do not label the fit delta pose-only.
- Report the first divergence in phases: sizing/outline; item order/prefix; guidance; visit template/requested origin; clipping; fit/score/incumbent; selected footprint; compactor output. This identifies where observed behavior first separates without asserting a counterfactual search result.

This separates the three questions as far as observation allows:

1. **Conservative outline/sizing:** compare per-item demand and extent maxima and the derived target/outline before any visit. Seed 42 already shows a candidate-1 outline change; seed 3 shows the same +3,000 demand but unchanged final outline. For seed 3, still inspect `boundaryX`, width/height maxima and targets because demand feeds more than the final outline. An outline or boundary change before the first visit is a sizing-path divergence; it does not prove sizing alone caused routed area/copper/via changes.
2. **Former TOP0 visit opportunities:** align ring/fallback ordinals and log both pre-clipping requested origins and post-clipping origins. Odd policy-1 visits replace the corresponding policy-0 TOP0 test. The policy-0 run records what actually happened at that TOP0 visit; policy 1 does not test the counterfactual TOP0 pose. Changed clipped origin can be attributed to active-envelope clipping only when the request and preceding state match. If prior placement or outline differs, later origins are downstream effects and cannot be called isolated lost-origin effects.
3. **TOP0 guidance/centering:** the captured `preferredX/Y`, pad target, support anchors, vacancy source envelope and pocket establish whether target selection still came from TOP0 while the trial template was TOP90. This proves the dataflow and quantifies any target/trial offset. It cannot prove the guidance was suboptimal or that different guidance would improve routed geometry without an expressly authorized counterfactual experiment.

## Limits

The existing run proves a strict regression on two rows and records the changed placement/routing metrics. Source inspection proves that policy 1 changes conservative sizing and alternates the active template at existing visits while retaining TOP0 advisory inputs. A paired observer can locate the first observable divergence and, when all preceding state is equal, attribute that local fit/score change to the actual substituted pose or envelope clipping. It cannot establish which heuristic is globally best, prove a counterfactual TOP0/TOP90 result at an unvisited point, or apportion final routed deltas across sizing, orientation, later placement, compaction, and routing. Those claims need separate authorized experiments and independent acceptance; this note does not authorize them.
