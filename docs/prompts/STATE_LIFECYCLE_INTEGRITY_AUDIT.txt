==================================================
GOAL
==================================================

Determine whether TroubleshootJS's growing set of mutable runtime systems can enter contradictory, contaminated, orphaned, or impossible states when the player performs unusual but legal action sequences.

The central question is:

"Can a player, verifier, or lifecycle transition leave the physical board, CircuitJS graph, fault ownership, inventory, instruments, power/control state, damage state, repair state, and challenge/session state disagreeing with one another?"

This audit should treat TroubleshootJS as a STATE MACHINE, not merely a collection of individually correct features.

The project now has many interacting state dimensions, including:
- generated fault ownership;
- effective generated fault state;
- physical original/replacement identity;
- mounted / removed / loose state;
- lifted / connected terminal state;
- private fault infrastructure;
- secondary stress/damage state;
- board power state;
- external control command state;
- simulation RUN/STOP state;
- stored energy / discharge readiness;
- active resistance/continuity/diode measurement stimulus;
- passive DC meter loading;
- retained probe identity;
- runtime physical-part registries;
- catalogs and acquired replacement inventory;
- challenge READY / repair / customer retest / Finish Job / COMPLETED state;
- Quick Play session identity;
- developer verification transactions.

Each subsystem may be locally correct while combinations still fail.

The audit should therefore focus heavily on ADVERSARIAL SEQUENCES and transition invariants.

==================================================
2. DEFINE CROSS-SYSTEM INVARIANTS
==================================================

Extract the invariants the current architecture intends to maintain.

Examples to investigate and refine:

PHYSICAL / SOLVER IDENTITY
- every mounted physical part has exactly the intended solver backing;
- every solver-owned replaceable part belongs to exactly one physical part;
- a removed/lifted part must not remain electrically connected except through explicitly modeled retained fault infrastructure;
- a visual reconnection must correspond to real graph reconnection;
- a physical part's immutable provenance/identity must not change because of mounting state.

GENERATED FAULT OWNERSHIP
- the original generated fault stays with the original physical owner unless the fault model explicitly says otherwise;
- removal, lift, reconnect, reinstall, measurement, or session verification cannot silently cure the generated fault;
- a catalog replacement must not inherit the original's private generated-fault infrastructure;
- generated fault metadata must not become equivalent to current physical health.

SECONDARY DAMAGE
- secondary damage belongs to the actual damaged physical part;
- removal/reinstall of a damaged part preserves its damage where physically appropriate;
- replacing a damaged part does not transfer its damage to a new part;
- secondary damage cannot be erased merely because the original generated fault was repaired;
- Finish Job/customer retest must fail when meaningful secondary damage still prevents correct behavior.

POWER / MEASUREMENT
- active meter stimulus and external board power must never coexist when prohibited;
- board-power-on must cancel/restore temporary active measurement first;
- temporary measurement infrastructure must always be removed;
- measurement cleanup must restore the exact prior valid power/control/runtime state;
- RUN/STOP must remain distinct from electrical power state;
- stored-energy safety must remain valid across measurement mode changes and physical mutations.

PROBES
- retained probes follow stable physical/logical identity only while that target remains physically meaningful;
- removal/lift/replacement cannot cause a probe marker to silently sample a different physical part;
- a replacement with the same logical slot does not automatically become the original physical probe target unless explicitly intended;
- stale endpoints must invalidate rather than return believable wrong values.

INVENTORY
- every acquired replacement has unique physical identity;
- installed/loose/inventory membership is mutually coherent;
- a single physical part cannot appear installed and loose simultaneously;
- session reset cannot retain acquired parts unless intentionally designed;
- catalog definitions and acquired physical instances remain distinct.

CHALLENGE LIFECYCLE
- READY cannot coexist with incomplete preparation/fault installation;
- successful repair status is not the same as latched job completion;
- customer retest must evaluate the live repaired board, not stale prior verification;
- Finish Job must not clear faults/damage as a side effect;
- completion of one challenge cannot mutate the next challenge;
- fresh Quick Play begins from a clean runtime envelope.

VERIFIER TRANSACTIONS
- developer diagnostics may temporarily mutate state but must restore it exactly;
- restoration failures must not leave hidden partial state that normal play continues from;
- verification must not become the owner of gameplay state.

Document the actual current invariants, not only these examples.

4. ADVERSARIAL PLAYER-SEQUENCE TESTING
==================================================

This is the most important practical section.

Exercise representative legal and near-boundary sequences designed to expose interaction bugs.

Do not limit yourself to the happy path documented by task acceptance.

Examples:

A. ORIGINAL FAULT OWNER ROUND-TRIP
1. Start a faulted challenge.
2. Power off safely.
3. Lift one lead of the original fault-owning part.
4. Measure it.
5. Reconnect it.
6. Remove it.
7. Measure it loose.
8. Reinstall it.
9. Power on.
10. Confirm its original fault still exists electrically and physically.

B. REPLACEMENT IDENTITY ROUND-TRIP
1. Remove original fault owner.
2. Acquire replacement A.
3. Install A.
4. Remove A.
5. Reinstall original.
6. Remove original again.
7. Install A again.
8. Acquire replacement B.
9. Swap A/B through the same slot.
10. Verify solver identity, provenance, fault state, and loose-part measurements remain attached to the correct physical instance.

C. SECONDARY DAMAGE ROUND-TRIP
1. Create a legal wrong replacement that can accumulate stress.
2. Power it long enough to become damaged/failed using the project's permitted deterministic developer acceleration where needed.
3. Power off.
4. Remove it.
5. Measure it loose.
6. Reinstall it.
7. Confirm damage persists.
8. Replace it with a correct fresh part.
9. Confirm damage does not transfer.
10. Reinstall the damaged part and confirm it is still damaged.

D. ACTIVE METER / POWER RACE
1. Power board off.
2. Begin resistance/continuity/diode transaction.
3. Attempt power-on during the transaction or at sensitive lifecycle moments.
4. Confirm measurement infrastructure is removed before external power reconnects.
5. Confirm no temporary elements remain.
6. Confirm probes and valid prior state are restored.

E. STORED ENERGY / MUTATION INTERACTION
1. Charge an RC challenge.
2. Power off while energy remains.
3. Attempt active measurement, lift/remove, and mode switching around readiness boundaries.
4. Confirm no unsafe active stimulus is admitted.
5. Confirm discharge/readiness state cannot become stale after graph mutation.

F. PROBE IDENTITY THROUGH MUTATION
1. Place probes on installed leads/pads.
2. Lift/remove target part.
3. Reconnect/reinstall it.
4. Replace with a distinct physical part.
5. Observe whether retained probes invalidate, persist, or rebind according to intended physical identity.
6. Ensure no plausible-looking stale value is produced from the wrong endpoint.

G. COMPLETION WITH RESIDUAL STATE
1. Repair generated fault.
2. Leave a separate wrong/damaged state if current mechanics permit it.
3. Invoke customer retest / Finish Job.
4. Verify completion reflects the entire live board state, not only generated fault metadata.

H. FRESH SESSION CONTAMINATION
1. Perform substantial modifications, acquire replacements, place probes, change instruments/control state, and possibly accumulate damage.
2. Complete or abandon the challenge through supported paths.
3. Start a fresh Quick Play challenge.
4. Confirm no old physical part, inventory item, probe, meter overlay, external command state, damage, fault binding, selection, or solver element persists.

I. PAUSE/RESUME EDGE CASES
Repeat representative power, measurement, fault, and repair transitions while simulation is paused and then resumed.
Determine whether verification waits correctly or stale state is accepted.

J. RAPID / REPEATED ACTIONS
Where the UI/controller permits it, repeat toggles or actions before prior verification settles:
- power off/on/off;
- control HIGH/LOW/HIGH;
- instrument enter/exit;
- remove/reinstall;
- retest repeated;
- Finish Job repeated.

Determine whether actions are serialized, rejected, idempotent, or capable of producing split state.

Not every sequence must be supported. If an action is correctly rejected, record the admission boundary and why it is safe.

==================================================
8. ASYNCHRONOUS / REANALYSIS / VERIFICATION ORDERING
==================================================

TroubleshootJS often mutates a CircuitJS graph, requests reanalysis, waits for simulation time/state, and then verifies.

Audit for race/order hazards such as:
- validator reading pre-analysis volts/current after mutation;
- multiple pending verification requests collapsing incorrectly;
- a later action happening while an earlier verification still assumes old topology;
- paused simulation preventing state settlement but lifecycle moving forward;
- stale repair status used by Finish Job;
- retest changing controls/power and failing to restore state on error;
- temporal validator and meter transaction competing for graph ownership;
- browser/UI reporting READY or repaired before electrical state has actually settled.

Identify whether there is a central transaction/epoch/generation concept or whether correctness relies on informal ordering.

Recommend one only if evidence shows it is needed. Do not invent architecture for its own sake.
